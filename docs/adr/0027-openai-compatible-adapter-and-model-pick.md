# ADR 0027: The openai_compatible adapter, and the OpenAI model pick

Status: accepted for OpenAI (model pick confirmed by Joe P on 2026-10-30); the LM Studio findings are partly verified (card C4)

## Decision
- One adapter, `openai_compatible`, serves OpenAI and LM Studio through the chat completions endpoint. A loopback `base_url` is a local server (LM Studio). No `base_url` means `https://api.openai.com/v1`, and any other host needs `allow_remote = true`.
- A remote host needs `api_key_env`, and the variable must be set. A remote host also needs `input_usd_per_mtok` and `output_usd_per_mtok`, so the budget guard can price a call. There is no built in price table: a model price that goes stale in code would make the guard wrong without warning, so the prices are settings.
- A remote `base_url` must be https, because the bearer key goes in a header.
- Output uses `response_format` of type `json_schema` with `strict: true`. The schema comes from the pydantic model with every property listed as required and unsupported keywords removed ([strict_schema.py](../../src/cypress_creek/providers/strict_schema.py)). Optional fields stay nullable. The reply is still parsed with the original model, so a dropped constraint is still enforced locally.
- `capabilities.strict_schema` is true for a remote host and, since 2026-10-30, for a loopback one: it was false until LM Studio 0.4.17 was seen to enforce a schema (see "Verified for OpenAI, partly verified for LM Studio" below). Other local servers are untested. Replies are validated against the schema either way.
- The truncation guard has three parts: the pre-flight estimate against the declared `context_tokens`, a reported `prompt_tokens` at or above the window, and an HTTP 400 whose body names a context length problem.
- Hosted requests use `max_completion_tokens` and send no temperature. Loopback requests use `max_tokens` and temperature 0.
- The `local_only` filter is not in the adapter. `build_prompt` already drops `local_only` facts when `capabilities.local` is false, and this adapter reports `local` false for any non loopback host. A component test builds a hosted request from a real prompt and checks the fact is absent.

## The model pick (external content, confirmed by Joe P on 2026-10-30)
The card says to choose the OpenAI model from the live models page, not from memory. On 2026-10-29 the page https://developers.openai.com/api/docs/models listed four models: `gpt-6-astra` ($10 input, $50 output per million tokens), `gpt-6.1-sol` ($2 and $10), `gpt-6.1-terra` ($1 and $5) and `gpt-6-luna` ($0.10 and $0.50), all with a 1.05M token context window. The smallest and cheapest is `gpt-6-luna`, described there as the most efficient model for focused, high volume tasks, so it is the working pick and the one the live test uses by default. The page did not say which models support `json_schema`. The structured outputs guide says the Chat Completions API supports it, but names only older models as examples. Whether `gpt-6-luna` honors strict `json_schema` is therefore unverified until the OpenAI live test passes with a real key.

This text came from a web page, so treat the model name and prices as data to confirm, not as fact. The model is a setting (`model`), and so are the prices. Changing the pick changes configuration and the `CYPRESS_CREEK_OPENAI_MODEL` variable the live test reads, not code. Joe P confirmed the pick `gpt-6-luna` on 2026-10-30. He confirmed the prices ($0.10 input and $0.50 output per million tokens) too. They are settings, so he can change them.

## Verified for OpenAI and for LM Studio 0.4.17
On 2026-10-30 Joe P ran `uv run pytest tests/integration -m live_openai -q` against the real OpenAI API with the test's default settings and it passed (`1 passed`). The real request shape (`response_format` with `json_schema`, `max_completion_tokens`, no temperature) was therefore accepted by the server for that run. A separate curl probe the same day, with the same request shape and no temperature, returned HTTP 200 from `gpt-6-luna` (the response names the model), the content `{"text":"Hello! How can I help?"}` and usage of 39 prompt and 18 completion tokens. He confirmed the pick afterwards (see above).

On the same day Joe P ran the two `live_lmstudio` tests against his LM Studio and both passed: a structured request returned a conforming object with real usage, and a prompt far longer than the loaded context was detected as `ContextTruncated`. The server was LM Studio 0.4.17 (Build 4) with the model `gemma-4-e4b` loaded at a context length of 8192, the same value passed to the tests. He then recorded the server's overflow reply: an error body whose `error` is the string "The number of tokens to keep from the initial prompt is greater than the context length (n_keep: 20015>= n_ctx: 8192). Try to load the model with a larger context length, or provide a shorter input." The existing `context length` marker matches that text and a component test pins it. The HTTP status was not shown. Two more probes the same day, run by Joe P by hand: a request whose prompt asked for a value the schema forbids (an enum of alpha and beta, prompt asking for gamma) came back `alpha`, so LM Studio 0.4.17 enforces `json_schema` for this model (one probe), and `strict_schema` is now true for loopback; and LM Studio's own listing `/api/v0/models` reports `loaded_context_length` (8192 for the loaded model, `max_context_length` 131072). The adapter reads it once when it is built: with no `context_tokens` configured it uses the loaded value, a configured value at or below it wins, and a configured value above it is refused with a `ConfigError`. A server without that endpoint changes nothing. The other entries of `CONTEXT_ERROR_MARKERS` remain guesses. The three questions the card names (context length handling, whether `json_schema` is honored, and how a context overflow is reported) are open. The `live_lmstudio` tests answer them when Joe P runs them against his LM Studio, and the findings section in docs/providers.md must then be filled in. The error text markers in `CONTEXT_ERROR_MARKERS` are guesses at server wording, not recordings (the odd phrase "context the overflows" is a recalled LM Studio message, kept only because it was seen once and costs nothing if it never matches).

## Limits
- A 400 is mapped to `ContextTruncated` purely by matching the server's text against `CONTEXT_ERROR_MARKERS`. A false match turns an ordinary 400 into a context error. That fails closed (the call stops), but the error is then misleading.
- Hosted calls send no temperature, so a published OpenAI result is not temperature pinned the way the method rule asks (temperature 0). This cannot be fixed for `gpt-6-luna`: on 2026-10-30 Joe P sent it `temperature: 0` and it answered HTTP 400, "Unsupported value: 'temperature' does not support 0 with this model. Only the default (1) value is supported." (`param: temperature`, `code: unsupported_value`). The model runs at its fixed default of 1, so an OpenAI row of the comparison varies between repeats by design, and the comparison table must say so. Joe P accepted this limit on 2026-10-30.
- The estimate is characters divided by 3, which can undercount dense text. The reported prompt count check only fires when the server reports a count at or above the window.
- `temperature` is not sent to a hosted server, so hosted output is not pinned to a fixed temperature.
- A hosted server that rejects `max_completion_tokens` or `json_schema` fails with `ProviderUnavailable` carrying the status and a bounded body.
